# ADR-0008 节点运行时做源码级裁剪，并维护一份可重放的偏差台账

> 状态：**已采纳**（2026-11-21）。第二节的死字节已全部删除并实测（408.2 → 267.4 MiB
> 解包，87.6 → 57.9 MiB 归档）；第三节的补丁链已落地为 `scripts/node-patches.mjs` +
> `patches/node/` + `docs/node-patches.zh.md`。**第六节当时是空的，build 7 填上了第一批**：
> 两条上游缺陷（Team 写作用域警告、fork 子会话首轮无继承）以补丁 0001/0002 落地，
> `RUNTIME_BUILD` 6 → 7，归档 58.2 MiB / 25 167 文件。台账见
> [`node-patches.zh.md`](../packages/dsh-remote-node-harness/docs/node-patches.zh.md)。
> 上承 [ADR-0007](adr-0007-fork-node-runtime.zh.md)，**推翻其 §五「不改上游语义、裁剪只是打包步骤」**。
> 本文只决定「节点那棵树改到多深、怎么记录、上游发版时怎么重放」，不改插件侧任何东西。

## 一、问题：现在的「自建运行时」只裁到包和文件，一行源码都没碰

ADR-0007 落地后，fork 相对上游 tag `dsh-v0.2.2-rc.5` 的全部改动是**一个提交、一个文件**：

```
scripts/release/verify-packed-install.ts   +14 −2
```

而且那个文件是**构建脚本**，不进归档（实测：归档里 `./scripts/**` 计数为 0）。也就是说：

**节点上跑的那棵树，源码与上游发布版逐字节相同。** 本项目对「节点该是什么」的主张，
目前只落在两处：组合层（`@local/rnh-brain` 决定加载哪些行）与打包步骤（`DROP_RULES`
删包、`ARTEFACT_RESIDUE` 删残留文件）。

用户的原话是「只留下必要的功能，把无用功能还有死代码移除」。包级的「无用」已经删了
（119 个包 / 1605.4 MiB），但**包内的「无用」一个都没删** —— 因为删包不会删进包里。

## 二、先算清楚还剩多少死字节（本轮实测，全部对着已发布的归档数）

408.2 MiB / 41 846 文件里，以下几类**没有任何运行时代码会读**：

| 类目 | 文件数 | 体积 | 为什么是死的 | 证据 |
|---|---|---|---|---|
| 非声明 `.ts` 源码 | 9 534 | 91.9 MiB | 只有 `src/**.ts`；运行时加载 `lib/**.js` | 322 个包逐个查 `main`/`exports`/`bin`：无一指向 `.ts` 或 `./src/` 下的可执行文件；全树 `*.js/*.cjs/*.mjs` 里没有一条 import 走 `@deepseek-ai/*/src/` |
| `.d.cts` 类型声明 | 7 110 | 22.7 MiB | 类型文件，运行时不需要 | `ARTEFACT_RESIDUE` 只写了 `.d.ts` 与 `.d.mts`，漏了 `.cts` |
| 其他 `.md` 文档 | 615 | 5.4 MiB | 文档 | `/(^|\/)\.md$/` 只匹配**文件名恰好叫 `.md`** 的文件；`guide.md`、`HISTORY.md` 全都漏了。README/CHANGELOG 由另外两条规则挡住（实测残留 7 个 `README_*.md` 在 `.history/` 下，也没挡住） |
| `.pdb` 调试符号 | 4 | 19.8 MiB | 只在 Windows 调试器里有意义，这是 linux 归档 | `node-pty/prebuilds/win32-*/conpty*.pdb` |
| 非本平台 prebuilds | 12 | 22.9 MiB | linux 归档里的 win32/darwin 二进制 | `node-pty/prebuilds/{win32-x64,win32-arm64,darwin-*}` |

**合计约 162.7 MiB（去重叠后约 140 MiB），占 408.2 MiB 的三分之一以上。**

这不是猜测：数字来自对已发布归档逐个条目称重（40 万字节级误差以内），
「`.ts` 是不是真死」另外用两种独立方法验过（manifest 入口扫描 + 运行时 import 扫描）。

### 落地后的实测结果

| | build 4（上游字节） | build 5（本轮） |
|---|---|---|
| 解包 | 408.2 MiB / 41 846 文件 | **267.4 MiB / 25 038 文件** |
| 归档 | 87.6 MiB | **57.9 MiB** |
| 死字节（五类合计） | 17 245 个 / 139.8 MiB | **0 个 / 0 MiB**（跨平台二进制单列，另 5.6 MiB） |

`dsh/docs/` 的 481 个文件（4.66 MiB）被**保留**：没有代码读它们，但 `dsh-doc` skill 在
节点组合里，它让读者去打开这些路径。删了等于留一个指着空的 skill。这是第二节表格之外
唯一的例外，也是本轮唯一一次「量出来是死的、判断后决定留」的地方。

验收是 **A/B**，不是「看起来还在」：同一份大脑组合分别喂两棵树，10 个端点的状态码与
响应体逐字节相同（见 `docs/ARCHITECTURE.md` 该节表格）。另外 build 5 在 Linux（WSL
Ubuntu 24.04 + Node 24.15）里解包启动，打印 `dsh web:`，换 cookie 得 200，
`POST /api/session/list` 返回 `{"items":[]}`。

## 三、决定

### 1. 裁剪下沉到三种粒度，而不是只删包

| 粒度 | 手段 | 谁受影响 |
|---|---|---|
| 包 | `DROP_RULES`（已有） | 与上游的**包集合**不同 |
| 文件 | `ARTEFACT_RESIDUE`（已有，本轮修 bug 并扩类目） | 与上游的**同一包内文件集合**不同 |
| 源码 | **新增**：`NODE_PATCHES` 补丁链，改上游源码 | 与上游的**源代码**不同 |

前两种是「删」，第三种是「改」。用户要的「无用功能移除」多数落在第三种 ——
比如一个包的某个模块只在浏览器面被 import，删包不行（包还被 host 面用着），
删文件有风险（模块图是动态的），**删导出的那个函数才是对的**。

### 2. 源码改动一律走补丁链，不直接改 fork 的工作树

理由很实际：fork 是上游仓库的完整副本，直接在上面改提交，升级时要手工辨别
「哪些提交是本项目的、哪些是上游的」，而 `git diff <tag>..<branch>` 一旦夹进上游的
新提交就再也说不清。补丁链把「改了哪几行」变成可数的对象：

```
packages/dsh-remote-node-harness/patches/node/
  0001-drop-browser-only-export.patch       ← 每个补丁一个文件，标准 unified diff
  0002-....patch
```

构建时 `git -C <fork> apply --3way`，失败就**停下并报告**，绝不 `--reject` 静默跳过。
好处：任何一个补丁单独可读、单独可测、单独可弃；上游一改，冲突精确定位到某个补丁。

### 3. 台账：每个补丁必须有一行记录，缺一行就不许合并

新增 `docs/node-patches.zh.md`，与 `patches/node/*.patch` **一一对应**（有断言守住）。
每条记录六件事：

| 字段 | 回答什么 |
|---|---|
| 编号 / 文件 | 哪个补丁 |
| 改哪个包、哪个文件、哪几行 | 定位 |
| 移除了什么 | 行为变化 |
| 为什么节点不需要 | **理由**（写不出理由的补丁不许进） |
| 怎么验证没坏 | 验收命令或实测记录 |
| 上游若修了同一处怎么办 | 冲突处置 |

最后一条是用户问题的核心：「后续 DSH 查漏补缺修 bug 时，也要求其进行相同的修复」。
补丁链保证**上游的修复一定进入本项目的树**（补丁是叠加在上游之上的），而台账保证
**本项目自己的改动不会因为升级丢失**（重放失败即报错，不静默）。

### 4. `RUNTIME_BUILD` 必须跟着升

源码改动的字节差异比删包更难察觉：同一个 `0.2.2-rc.5`、同样的包集合，行为不同。
所以每加一个补丁或改一条残留规则都要 +1，这是既有的规则（`artefact.js` 的注释已写明），
build 5 执行时升到 5；build 6 改的是安装脚本，虽然归档字节没变也升到 6；
**build 7 加了两条补丁，升到 7**。

## 四、验收

| 项 | 怎么算过 | 结果 |
|---|---|---|
| 死字节确实没了 | 重建归档，逐类目重数，与第二节的表对齐 | **过**：五类全为 0 |
| 树还能当大脑启动 | 解包后 `--host 127.0.0.1 --port 0 --no-open` 打印 `dsh web: <url>`；换 cookie 得 303；`POST /api/session/list` 得 200 | **过**（WSL Ubuntu 24.04 / Node 24.15.0） |
| 删的东西没改变任何回答 | 同组合分别喂 build 4 与 build 5，逐端点比状态码与响应体 | **过**：10 个端点差 0 个 |
| 补丁链能重放 | 在一个真 git 仓库上验四种情形：首次应用、已应用、上游把 hunk 挪位、上游改写同一行 | **过**（`node-patches-unit`，四种情形各自一条断言，冲突时还断言没有 `.rej`/`.orig` 落地） |
| 台账与补丁一一对应 | `patches/node/*.patch` 的文件名集合 == 台账编号集合 | **过**（build 5/6 两边都是空集；build 7 起两边都是 2 条，且 `node-patches-unit` 按名字断言了这个集合） |
| 每个补丁有理由 | 台账每行六个字段都非空 | **过** |

## 五、非目标

- **不改路由、身份、会话语义。** 那是插件侧（`packages/dsh-remote-node-harness/src`）的事，
  与运行时树无关。
- **不为桌面端裁。** 桌面端跑官方发行版，节点树可以更狠。
- **不做 per-node 的树。** 仍然一份产物所有节点共用。
- **不碰上游的 `exports` 契约形状。** 删导出的函数可以，删 `exports` 键不行 ——
  那会让 `require` 的解析路径变化，属于另一类风险。

## 六、源码级补丁：第一批候选，以及 build 7 实际落了什么

**这一节当时是空的，而空着是对的**：能表达成「删包」或「删文件」的东西不该写成补丁，
更容易审、更容易回退、也不需要重放。为了填一行而硬改源码，是把机制用成装饰。

**build 7 落下的两条不是「裁剪」，是「修 bug」**，这也是它们够格进补丁链的原因：
它们不属于任何一条删包/删文件规则能表达的东西，且都已在真实使用中暴露。

| 补丁 | 改了什么 | 为什么必须以补丁形式存在 |
|---|---|---|
| `0001-team-write-scope-overlap-all-live-tasks.patch` | `projectTaskView` 的写作用域比对从「只比 `in_progress`」改为「比每一条非 `deleted` 的任务」，警告带对方状态 | 上游行为本身是缺陷：兄弟任务一完成，重叠警告就消失，调用方读到「无冲突」而文件刚被写过。删包表达不了，只能改这一行逻辑 |
| `0002-fork-seed-covers-requesting-turn.patch` | fork provider 的切点从「最后一个 `turn/end`」改为「最后一条携带未应答 tool-call 的 `assistant/message` 之前」，用 `buildForkSeed` 收口；工具措辞随之改准 | 同上：首轮/轮次中途委派时子 agent 拿到空 seed，而工具描述向模型承诺了继承。这是判断错误，不是冗余代码 |

下面这批「裁剪」候选仍然没动，理由不变：

| 候选 | 体量 | 为什么还没做 |
|---|---|---|
| 21 个包声明了 `dsh.client`，其中 20 个的 `./client` 导出**没有任何运行时文件 import**（`dsh-api-gateway/client` 是唯一被宿主 import 的，必须留） | 1 955 KiB | 「没有 import」不等于「没有读者」：这些半边的消费者是浏览器，`dsh-client-modules` 通过 `window.__ModuleLoader__` 装配。删导出会不会让桌面端 `dsh.client` 扫描拿到空模块，需要先读装配逻辑 |
| `@deepseek-ai/dsh-sandbox-windows-acl` 整个包（节点是 linux） | 14 个文件 | 它在 `dsh-base` 的 `cordis.patch.yml` 里被 `process.platform === 'win32'` 挡住，所以「不加载」不等于「可以删」。删包属打包步骤，但它在 `@deepseek-ai` 作用域内、当前 `DROP_RULES` 没覆盖 —— 应该先加一条包规则，而不是写补丁 |
| `node_modules/.bin/*.cmd` / `*.ps1`（Windows shim，26 个） | 15 KB | 太小，且属于「按平台删文件」而非「改源码」，走 `ARTEFACT_RESIDUE` 的 `.cmd`/`.ps1` 规则更合适 |
